cyan_reditools.R:
------------------
CYAN_run_reditools(bam, reference, output_dir, work_dir=tempdir(),
                   sample_name=NULL, strand_mode=0L, min_coverage=1L,
                   min_base_quality=30L, min_read_quality=20L,
                   min_read_length=30L, min_edits=0L, strict=FALSE,
                   region=NULL, omopolymeric_file=NULL, splicing_file=NULL,
                   bed_file=NULL, require_dup_marked=TRUE, keep_tmp=FALSE,
                   save_rds=TRUE, verbose=TRUE, debug=FALSE)
  - Runs REDItools2 (pysam-based pileup engine) on one BAM via a managed
    basilisk Python env; detects RNA-editing-type substitutions relative to
    the reference
  - Checkpoints raw tab-delimited REDItools2 output to
    <output_dir>/<sample>_reditools.txt before parsing -- expensive pileup
    is never lost. On a subsequent call, an existing raw_out checkpoint is
    detected and only RE-PARSED (REDItools2 itself is not re-run), so fixing
    a parsing bug or re-deriving the substitutions-only table is cheap
  - Parsed/returned/RDS'd result (cyan_editing_result) is ALWAYS
    substitution-rows-only (all_subs != "-"), regardless of the strict value
    the raw file was generated with -- the full covered-position table
    (needed e.g. for APOBEC-signature background work) only ever exists in
    the raw .txt checkpoint, not in-memory or in the RDS
  - require_dup_marked=TRUE (default) hard-stops unless the BAM has at least
    one SAM FLAG 0x400 read -- REDItools2's own duplicate filter is a silent
    no-op on a BAM that was never duplicate-marked upstream
  - bed_file: restricts which positions are WRITTEN to output -- it does
    NOT restrict the scan range; without a region, the underlying pysam
    fetch() is unbounded and every read in the BAM is walked base-by-base
    regardless of how few BED sites were requested. CYAN_flag_germline_variants()
    used to reuse this function as the WGS-side pileup engine via bed_file
    alone -- confirmed (2026-11-03) to take hours on just ~150 sites because
    of this. It now uses CYAN_run_targeted_pileup() (cyan_targeted_pileup.R)
    instead; see that section below.
  - Output: <sample>_reditools.txt (raw checkpoint, all covered positions),
    <sample>_reditools_subs.txt (substitution rows only),
    <sample>_reditools.rds (parsed cyan_editing_result, if save_rds=TRUE)

CYAN_run_reditools_batch(bam, reference, output_dir, ..., verbose=TRUE)
  - Loops CYAN_run_reditools() over a named vector of BAM paths (names =
    sample labels); per-sample failures are caught and warned on, not fatal
    to the batch
  - Returns a cyan_batch_result: named list, one cyan_editing_result (or
    NULL on failure) per sample

print.cyan_editing_result(x, ...) / print.cyan_batch_result(x, ...)
  - S3 print methods; batch summary shared between
    CYAN_run_reditools_batch() and CYAN_flag_germline_variants_batch()
    (both return class cyan_batch_result)

.cyan_parse_reditools_output(path, chunk_size=10e6)  [internal]
  - Streams the raw REDItools2 .txt in line chunks (data.table::fread() per
    chunk), filters to substitution rows, splits the BaseCount column into
    count_A/count_C/count_G/count_T (data.table::tstrsplit(), vectorised)
  - Chunked/vectorised specifically because the prior read.table() +
    strsplit()+do.call(rbind,.) approach OOM'd on a 37GB strict=FALSE raw
    file with 58GB RAM available (2026-10-14)
  - col_map normalises REDItools2's raw header names across versions.
    BUG FIXED 2026-11-02: the map only had "BaseCount[ACGT]" (no commas) as
    a key, but REDItools2's actual header is "BaseCount[A,C,G,T]" (commas
    between letters) -- the rename silently never matched, so count_A/C/G/T
    were silently absent from every parsed result (all samples, both the
    original strict=TRUE run and the strand_mode=2/strict=FALSE re-run) with
    no warning or error until a downstream consumer
    (CYAN_flag_germline_variants(), which requires those columns) hard-
    stopped on it. Fix: added "BaseCount[A,C,G,T]" as a second key mapping
    to the same "base_count" target, keeping the no-comma variant too in
    case some REDItools2 version genuinely emits it header-wise. Since raw
    .txt checkpoints are untouched by this, recovery is a cheap re-parse
    (CYAN_run_reditools()'s own cache-hit path), not a REDItools2 re-run.

cyan_targeted_pileup.R:
------------------------
CYAN_run_targeted_pileup(bam, reference=NULL, bed_file, output_dir,
                         work_dir=tempdir(), sample_name=NULL,
                         min_base_quality=30L, min_read_quality=20L,
                         min_read_length=30L, processes=1L,
                         require_dup_marked=TRUE,
                         keep_tmp=FALSE, save_rds=TRUE, verbose=TRUE,
                         debug=FALSE)
  - ADDED 2026-11-03. Computes coverage + per-base (A/C/G/T) read counts at
    a short, sparse list of known positions (bed_file) via pysam's indexed
    pileup seeked directly to each site -- O(sites) indexed lookups instead
    of REDItools2's O(genome length) base-by-base scan. Purpose-built to
    replace CYAN_run_reditools() as the WGS-side engine inside
    CYAN_flag_germline_variants(): REDItools2's bed_file only filters
    output, not the scan range (see cyan_reditools.R notes above) --
    confirmed to hang for hours on a 150-site test that this function
    completes in ~30 seconds on the same BAM/sites
  - FIXED 2026-11-04: the 150-site benchmark above did not reflect real
    candidate-list scale. A live production run (2,185,297 candidate sites,
    one sample) measured ~33 sites/sec (~18h for that one sample, 16
    samples in the batch -- days, not hours) -- each site was still paying
    one full pysam.pileup() call's htslib-seek + BGZF-decompression +
    object-construction overhead, even though the underlying base-level
    work is trivial. Real candidate lists cluster tightly (median gap ~70bp
    on this project's own S327 candidates, chr1), so
    inst/python/targeted_pileup.py now (a) merges sites within
    --merge-gap bp (default 1000) of each other into ONE pileup() call
    per window instead of one per site -- ~13x fewer calls on that same
    chr1 list -- and (b) splits windows across `processes` worker
    processes (new -p/--processes CLI flag, new `processes` R param,
    default 1L/sequential, forwarded transparently through
    CYAN_flag_germline_variants()'s/..._batch()'s existing `...`). Measured
    on a reconstructed full-chr1-scale candidate set (163,625 real-spaced
    sites) against the SAME BAM: old algorithm ~33 sites/sec -> new
    single-process ~324 sites/sec (windowing alone, ~10x) -> new
    10-process ~1518 sites/sec (~46x total). Output verified byte-for-byte
    identical to the pre-fix algorithm on a real 23,746-site subset, and
    identical across process counts (p=1 vs p=10) on the 163,625-site set
    -- windowing/parallelism changes call volume only, not which reads or
    bases are counted per site, or the result. Row order in the output
    file is no longer guaranteed to match bed_file's input order (grouped
    by merged window instead) -- .cyan_parse_targeted_pileup_output() does
    not depend on row order, so this is not a breaking change.
  - FIXED 2026-11-04 (second issue, same day): the first real multiprocess
    production run (S327, ~97% through) crashed with exit code 1. Root
    cause: this project's liftOver'd candidate BED labels the mitochondrial
    contig "M", but the BAM/reference FASTA both use "MT" -- the existing
    chr-prefix-only fallback in open_pileup()/ref_base_at() couldn't
    resolve that, so pysam.pileup() raised an uncaught ValueError in
    whichever worker hit the first mitochondrial window. That exception
    propagating out of multiprocessing.Pool.map() made the Pool's `with`
    block terminate every OTHER worker immediately too (Pool.__exit__ calls
    terminate()) -- which is why every chunk was sitting at ~97% done
    simultaneously rather than one finishing while the rest continued.
    Fixed by replacing the single hardcoded fallback with
    chrom_candidates(chrom) -- tries the name as given, its chr-prefix-
    swapped form, and (new) the M/MT synonym of both, in order, before
    giving up. Applied to both open_pileup() and ref_base_at() for
    consistency. Verified against the real BAM: M-chromosome sites that
    previously crashed now resolve correctly (e.g. position M:5001 ->
    6300x coverage, matching mitochondrial DNA's typically extreme
    sequencing depth) with exit code 0.
  - Read/base-level filtering ported from REDItools2's own
    filter_read()/filter_base() (unmapped/QC-fail/secondary/supplementary/
    duplicate exclusion, mapping quality, read length, proper-pair flag
    check, SA-tag chimeric-read exclusion, base quality) via a new bundled
    script (inst/python/targeted_pileup.py) -- NOT REDItools2 itself, no
    substitution/strand/omopolymeric/splicing logic, since the germline
    step never needed any of that
  - Every bed_file site is written exactly once, including zero-coverage
    ones (REDItools2 would simply omit uncovered positions) -- required so
    "no row" is never ambiguous for the germline-status classification
  - Same checkpoint-reuse pattern as CYAN_run_reditools(): an existing
    <sample>_targeted_pileup.txt in output_dir is re-parsed, not re-run
  - Reuses .cyan_reditools_env (basilisk) and .cyan_reditools_run() --
    those are generic Python-subprocess plumbing, not REDItools2-specific
  - Output: <sample>_targeted_pileup.txt (raw checkpoint),
    <sample>_targeted_pileup.rds (if save_rds=TRUE)

cyan_germline_variants.R:
--------------------------
CYAN_flag_germline_variants(rna_result, dna_bam, reference, output_dir,
                            work_dir=tempdir(), sample_name=NULL,
                            dna_min_coverage=10L, dna_min_alt_reads=3L,
                            dna_min_alt_freq=0.1, require_dup_marked=TRUE,
                            keep_tmp=FALSE, save_rds=TRUE, verbose=TRUE,
                            debug=FALSE, ...)
  - Cross-references RNA-editing candidates (from CYAN_run_reditools())
    against matched WGS data from the SAME individual to distinguish true
    post-transcriptional editing from germline variants
  - CHANGED 2026-11-03: WGS-side lookup now calls CYAN_run_targeted_pileup()
    instead of CYAN_run_reditools() -- same bed_file-of-candidate-positions
    input, same four appended output columns, but no longer scans the whole
    BAM to answer a 150-site question (see cyan_targeted_pileup.R above for
    the full rationale). The RNA-side call (CYAN_run_reditools() on the
    RNA-seq BAM, upstream of this function) is unaffected by this change.
  - rna_result and dna_bam MUST already share one coordinate system
    (contig naming AND genome build) -- this function does no liftover or
    build reconciliation itself; see rna_editing_germline.R (Mouse_A3B
    project) for a worked liftover-based wrapper when RNA and WGS data are
    on different builds
  - Per candidate: primary alt base (highest RNA-read-supported substitution
    at that position, via .cyan_primary_alt_base()) is looked up in the WGS
    pileup and classified: "germline" (WGS alt freq/reads above threshold),
    "confirmed_somatic" (WGS covered, reference-only), "undetermined" (WGS
    coverage below dna_min_coverage) -- never silently dropped
  - dna_min_coverage/dna_min_alt_reads/dna_min_alt_freq default to
    REDItoolDnaRna.py's own defaults (-c 10/-v 3/-N 0.1), carried over as a
    starting point, not independently re-derived -- verify before treating
    as settled
  - Output: <output_dir>/<sample>_germline_flagged.txt (candidate table),
    <sample>_germline_flagged.rds (full rna_result + 4 appended columns, if
    save_rds=TRUE)

CYAN_flag_germline_variants_batch(rna_results, dna_bam, reference,
                                  output_dir, ..., verbose=TRUE)
  - Loops CYAN_flag_germline_variants() over dna_bam (named vector, names =
    animal IDs); only animals present in dna_bam are processed -- samples
    with no WGS match are simply absent from dna_bam, no special-casing
    needed by the caller
  - Per-sample failures caught and warned on, not fatal to the batch
  - Returns a cyan_batch_result (same class/print method as
    CYAN_run_reditools_batch())

cyan_motif_editing.R:
----------------------
CYAN_scan_motif_editing(raw_reditools_path, reference, gtf, motif=NULL,
                         motif_position=NULL, alt_base=NULL, output_dir,
                         work_dir=tempdir(), sample_name=NULL,
                         control_motif=NULL, min_coverage=10L, region=NULL,
                         bed_file=NULL, chunk_size=10e6, save_rds=TRUE,
                         verbose=TRUE)
  - Motif-conditioned RNA-editing background/enrichment (e.g. APOBEC
    TCW/UCC). Builds a genome-wide catalog of every exonic occurrence of
    `motif` (transcript-oriented, via `gtf`'s exon strand -- deliberately
    NOT REDItools2's own per-row strand call, to stay independent of that
    project's earlier strand_mode=1/2 inversion bug), then streams a
    sample's RAW REDItools2 checkpoint (`{sample}_reditools.txt`, requires
    strict=FALSE -- NOT the parsed cyan_editing_result/RDS, which is always
    substitution-rows-only regardless of strict) to determine per-position
    coverage and (reusing the existing all_subs call, not a new threshold)
    edited status, for both the target motif and a control context (default:
    same base, any other flanking context). Returns site-level + per-group
    summary tables and an enrichment_ratio attribute.
  - motif/motif_position/alt_base have no default -- all required.
  - Two independent strand-correction steps per matched row: (1) undo
    REDItools2's own per-row 0/1/2 strand call to reach genomic (+); strand
    2 ("ambiguous") positions keep their coverage but get edited=NA; (2)
    apply the GTF strand to reach transcript orientation. Verified
    2026-11-05 against the real GRCm39 FASTA (strand 1 rows report
    Reference/AllSubs as-is on the genomic (+) strand, strand 0 rows report
    them complemented) and against a hand-built synthetic +/- strand
    fixture covering both correction steps, the target/control exclusion
    logic, and the zero-coverage ("never seen in the raw file") path.
  - Performance (benchmarked 2026-11-05 on a real 20M-line/1.1GB slice of
    this project's S327_reditools.txt, then two fixes applied): per-chunk
    parsing originally round-tripped `readLines()` lines through
    `paste(collapse="\n")` into `fread(text=<string>)` (mirroring
    .cyan_parse_reditools_output()'s existing pattern) -- fread's `text=`
    actually accepts the character vector directly, so dropping the paste
    cut per-chunk parse time from ~33s to ~8s. Separately, the sites table
    (can be catalog-sized -- every control position, covered or not, e.g.
    ~29M rows for TCC genome-wide) was written with `utils::write.csv()`
    (~49s at that scale) -- switched to `data.table::fwrite()` (~2.8s).
    Net result at real scale: ~6.5 min one-time catalog build (paid once
    by CYAN_scan_motif_editing_batch(), NOT per sample) + ~93 sec/GB
    per-sample streaming (dominated by readLines(), not further optimized
    -- readr::read_lines() looked faster in isolation but needs a binary
    connection, not pursued since it would mean restructuring the
    header-line handling and isn't a CYAN dependency yet).
  - Catalog excludes exon sequence annotated on both strands (overlapping
    antisense genes) entirely -- motif direction can't be resolved there.
  - ADDED 2026-11-13: `sites` now also carries `alt_count` (reads
    supporting `alt_base` at `motif_position`, same two-step strand
    correction as Reference/AllSubs above -- a strand flip relabels which
    base a count belongs to, A<->T/C<->G, applied to REDItools2's own raw
    `BaseCount[A,C,G,T]` field) and `frequency` (`alt_count / coverage`).
    Motivation (Mouse_A3B APOBEC analysis): `edited` is a presence/absence
    call gated only by `CYAN_run_reditools()`'s `min_edits` (1 supporting
    read is enough at that function's default of 0) -- confirmed on 4 real
    samples to scale almost 1:1 with mean coverage (e.g. target-motif edit
    RATE 1.79x higher in a sample with 1.66x the coverage of another, no
    consistent relationship to genotype), i.e. largely a depth artifact,
    not biology. `alt_count`/`frequency` let a caller apply their own
    depth-robust minimum-read-support/frequency threshold downstream
    instead, without a second raw-checkpoint streaming pass. `edited`
    itself is unchanged (still the project's one presence/absence
    definition) -- this is an addition, not a replacement. NA under the
    same conditions as `edited` (strand 2, or reference mismatch after
    correction), or when coverage is 0.
  - Fixed 2026-11-09: the per-sample result list used to build via
    `as.data.frame(sites)`, which copies the (potentially catalog-sized)
    `sites` data.table rather than converting it in place -- confirmed to
    OOM-kill the process on a real run (Mouse_A3B, 17-sample batch,
    killed ~60GB RSS on the last/largest sample, right between the
    fwrite() calls and saveRDS()). Now uses `data.table::setDF(sites)`
    (in-place conversion, no second copy).
  - Second, deeper fix the same day: that first fix only removed the
    per-sample transient doubling -- the real driver of the original crash
    was CYAN_scan_motif_editing_batch() itself accumulating every
    completed sample's full result (sites table included) into one
    in-memory list across the whole batch, so memory grew with every
    sample and the last one paid for all the ones before it. Confirmed by
    reproducing the same ~55-60GB RSS pattern (static free RAM, matches
    ~17 x one sample's sites-table size) when manually re-combining 17
    already-saved per-sample .rds files the same way. New `keep_sites`
    arg on CYAN_scan_motif_editing_batch() (default FALSE): drops each
    sample's `sites` from the returned list right after that sample's own
    on-disk outputs are written, bounding memory to ~one sample's sites
    table regardless of batch size. Full per-sample `sites` remain on disk
    (`_motif_sites.csv`, and `_motif_result.rds` if save_rds=TRUE) either
    way -- `keep_sites=TRUE` opts back into the old full-detail-in-memory
    behavior for small batches that want it.

CYAN_scan_motif_editing_batch(raw_reditools_paths, reference, gtf, motif=NULL,
                               motif_position=NULL, alt_base=NULL, output_dir,
                               control_motif=NULL, region=NULL, bed_file=NULL,
                               keep_sites=FALSE, verbose=TRUE, ...)
  - Builds the catalog once (sequence-only, doesn't depend on the sample)
    and reuses it across every sample. Per-sample failures warn and record
    NULL, remaining samples continue (same tolerance pattern as
    CYAN_run_reditools_batch()).

DEPENDENCIES / NOTES
================================================================================
- basilisk (Bioconductor, Imports): managed Python env for REDItools2 --
  see basilisk.R for pinned package versions
- reticulate (Imports): py_exe() to resolve the basilisk-managed Python
  binary before system2() calls
- data.table (Imports): chunked fread()/tstrsplit() parsing of large raw
  REDItools2 output -- required for strict=FALSE genome-wide runs, which
  can reach hundreds of millions of rows / tens of GB (see
  .cyan_parse_reditools_output() notes)
- GATK: external Java tool, invoked via system2("gatk", ...) once a
  MuTect2 wrapper exists -- not bundled/managed by CYAN (unlike REDItools2,
  which runs through basilisk)
- Positioned between HORIZON (upstream BAM processing -- duplicate-marking
  via HORIZON_mark_duplicates() is a precondition for
  require_dup_marked=TRUE) and GAIA/CAULDRON (downstream expression-level
  analysis); CYAN itself does not depend on either package
- One sample per call is the core design (CYAN_run_reditools(),
  CYAN_run_targeted_pileup(), CYAN_flag_germline_variants()); cohort
  looping is the batch wrappers' job, not baked into the core functions
- No liftover/genome-build reconciliation inside CYAN itself -- when RNA
  and matched WGS data are on different builds (e.g. Mouse_A3B:
  RNA on mm39, WGS on mm10), that reconciliation (liftOver + contig-name
  mapping) is a project-script-level concern, not something
  CYAN_flag_germline_variants() handles
- GenomicRanges, IRanges, BiocGenerics, Biostrings, Rsamtools, rtracklayer
  (Bioconductor, Imports as of 2026-11-05, added for
  cyan_motif_editing.R): all called fully `pkg::fun()`-qualified
  throughout that file -- no new NAMESPACE importFrom entries were needed,
  only the DESCRIPTION Imports additions (GenomicRanges moved there from
  Suggests)
